# 1주차: 메인 에이전트 vs 서브에이전트 vs 에이전트 팀 — 누가 무엇을 보는가

## 왜 이것을 배우는가?

Claude Code에게 큰 일을 시키면, 로그·검색 결과·파일 내용이 대화에 계속 쌓인다. 대화(컨텍스트)가 커질수록 중요한 정보가 묻히고 비용도 늘어난다.

Claude Code는 이 문제를 **일을 다른 에이전트에게 나눠 맡기는 방식**으로 푼다. 나눠 맡기는 방법이 두 가지 있다.

- **서브에이전트**: 메인 에이전트가 부하에게 일을 시키고 요약만 돌려받는다
- **에이전트 팀**: 여러 Claude 인스턴스가 서로 직접 대화하며 함께 일한다

이번 주에는 세 단위의 차이를 **"무엇을 보고, 누구와 말하고, 무엇을 돌려주는가"** 라는 하나의 축으로 정리한다.

---

## 1. 메인 에이전트 (메인 대화)

사용자가 직접 대화하는 Claude Code 세션 그 자체다.

- **보는 것**: 세션 전체 기록 — 지금까지의 대화, 호출한 스킬, 읽은 파일 전부
- **장점**: 사용자와 잦은 주고받기가 가능하다
- **단점**: 다시 볼 일 없는 출력까지 전부 컨텍스트에 쌓인다

> 💡 **스킬은 메인 컨텍스트에서 실행된다.** 스킬은 격리된 별도 에이전트가 아니라 메인 대화 안에서 동작한다. 서브에이전트와 혼동하지 말자.

---

## 2. 서브에이전트

### 2.1 정의

> "specialized AI assistants that handle specific types of tasks" — 공식 문서

서브에이전트는 **YAML frontmatter + 시스템 프롬프트**가 담긴 Markdown 파일 하나로 정의된다.

```markdown
---
name: log-analyzer
description: 빌드·테스트 로그를 읽고 실패 원인만 요약해 돌려준다
tools: Read, Grep, Glob
model: haiku
---

너는 로그 분석가다. 주어진 로그에서 실패한 지점과 원인만 찾아
5줄 이내로 요약해 보고한다. 로그 원문을 그대로 붙여 넣지 않는다.
```

### 2.2 언제 쓰는가

> "Use one when a side task would flood your main conversation with search results, logs, or file contents you won't reference again: the subagent does that work in its own context and returns only the summary."

핵심은 **"다시 볼 일 없는 장황한 출력"** 이다. 서브에이전트가 그 출력을 자기 컨텍스트에서 소화하고, 메인에는 **요약만** 돌려준다.

### 2.3 컨텍스트 격리 — 서브에이전트가 보지 못하는 것

> "It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read."

| 항목 | 메인 에이전트 | 서브에이전트 |
|------|--------------|-------------|
| 대화 기록 | 전부 본다 | 보지 못한다 |
| 시스템 프롬프트 | Claude Code 시스템 프롬프트 | 자기 프롬프트 + 기본 환경 정보만 |
| 이미 읽은 파일·호출한 스킬 | 기억한다 | 모른다 |
| 결과 전달 | 사용자에게 직접 | 요약만 메인으로 |

**실무 함의**: 서브에이전트는 메인 대화를 모르기 때문에, 일을 맡길 때 **필요한 맥락을 프롬프트에 직접 적어 줘야** 한다.

### 2.4 무엇을 물려받고, 무엇을 바꿀 수 있는가

| 설정 | 기본값 | 바꾸는 법 |
|------|-------|----------|
| 도구 | 부모 도구를 상속 | `tools`(허용 목록) / `disallowedTools`(차단 목록)로 **축소** |
| 권한 | `permissionMode`로 별도 지정 | 단, 메인이 `bypassPermissions`·`acceptEdits`·`auto`면 서브도 같은 모드 |
| 모델 | 부모 모델 | `model: haiku` 등으로 지정해 비용 조절 |

> ⚠️ 백그라운드로 실행되는 서브에이전트는 더 작은 내장 도구 세트를 쓴다.

### 2.5 실행 규칙

- **중첩**: 서브에이전트가 또 서브에이전트를 띄울 수 있다. 기본은 메인 아래 **3단계**까지
- **동시 실행**: 기본 **20개** (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`로 조정)
- **사용량**: 서브에이전트가 쓴 사용량도 같은 한도에 합산된다 — 공짜가 아니다

### 2.6 내장 서브에이전트

| 이름 | 역할 |
|------|------|
| Explore | 읽기 전용 검색 |
| Plan | 구현 계획 설계 |
| General-purpose | 범용 다단계 작업 |
| claude-code-guide | Claude Code 사용법 안내 |

### 2.7 정의 파일 위치와 우선순위

위에서부터 우선순위가 높다.

1. managed (조직 관리 설정)
2. `--agents` CLI 옵션
3. `.claude/agents/` (프로젝트)
4. `~/.claude/agents/` (사용자 전역)
5. 플러그인의 `agents/`

## 3. 에이전트 팀 (실험 기능)

### 3.1 정의

여러 Claude Code 인스턴스가 하나의 팀으로 일한다.

- 한 세션이 **Team lead**가 된다
- **팀원(Teammates)** 은 각자 컨텍스트로 독립 작업하고 **서로 직접 메시지**를 주고받는다
- 사용자도 팀원과 직접 대화할 수 있다

켜는 법: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`
> ⚠️ 비대화형 실행(`-p`, Agent SDK)에서는 팀원이 생성되지 않는다.

### 3.2 구성요소

| 구성요소 | 역할 |
|---------|------|
| Team lead | 팀을 만들고 이끄는 세션 (중간에 바꿀 수 없음) |
| Teammates | 독립 컨텍스트로 일하는 팀원 |
| Task list | 공유 작업 목록. 파일 락으로 작업을 claim한다 |
| Mailbox | 팀원 간 메시지함 (`~/.claude/teams/{team}/inboxes/{agent}.json`) |

팀원은 CLAUDE.md·MCP·스킬은 로드하지만, **lead의 대화 기록은 물려받지 않는다.**

### 3.3 제약

- 세션당 팀 1개
- 중첩 팀 불가 — 팀원은 팀원을 만들 수 없다
- `/resume` 시 in-process 팀원은 복원되지 않는다
- 권장 팀 크기: **3~5명**
- 서브에이전트 정의 파일을 팀원 역할로 재사용할 수 있다 (tools, model 등은 적용, skills는 미적용)

## 4. 서브에이전트 vs 에이전트 팀 — 공식 비교

| | 서브에이전트 | 에이전트 팀 |
|---|---|---|
| 컨텍스트 | 자기 컨텍스트, 결과는 호출자에게 반환 | 자기 컨텍스트, 완전히 독립 |
| 소통 | 호출자에게 결과 반환 (이름 붙은 서브끼리는 메시지 가능) | 팀원끼리 직접 메시지 |
| 조율 | 메인 에이전트가 모든 일을 관리 | 메시지 + 공유 작업 목록으로 스스로 조율 |
| 적합한 일 | 결과만 중요한 집중 작업 | 토론·협업이 필요한 복잡한 작업 |
| 토큰 비용 | 낮음: 결과가 요약되어 돌아옴 | 높음: 팀원 하나하나가 별도 Claude 인스턴스 |

> "Use subagents when you need quick, focused workers that report back. Use agent teams when teammates need to share findings, challenge each other, and coordinate on their own."

### 비유로 정리

- **메인 에이전트**: 프로젝트 담당자 본인
- **서브에이전트**: 담당자가 심부름을 보내는 조수. 조수는 지시서만 보고 일하고, 결과 보고서만 가져온다
- **에이전트 팀**: 회의실에 모인 동료들. 서로 의견을 주고받고 반박하며, 칸반 보드(작업 목록)에서 각자 일을 가져간다

---

## 5. 선택 기준 — 결정 흐름

```
사용자와 자주 주고받아야 하는가?
├─ 예 → 메인 대화에서 직접
└─ 아니오
   └─ 작업자끼리 발견을 공유하고 서로 반박·조율해야 하는가?
      ├─ 예 → 에이전트 팀 (비용 높음, 실험 기능)
      └─ 아니오 → 서브에이전트 (출력은 장황하고 결과만 필요할 때)
```

## 6. 실습

### 실습 1: 컨텍스트 격리 확인하기
1. 메인 대화에서 아무 파일 하나를 읽게 한다.
2. 내장 `Explore` 서브에이전트에게 "방금 읽은 파일이 뭐였지?"라고 묻게 한다.
3. 서브에이전트가 답하지 못하는 것을 확인한다. → 2.3절의 격리를 체감

### 실습 2: 첫 서브에이전트 만들기
1. 프로젝트에 `.claude/agents/log-analyzer.md`를 2.1절 예제대로 만든다.
2. 테스트를 일부러 실패시키고, "log-analyzer로 실패 원인을 찾아줘"라고 요청한다.
3. 메인 대화에 로그 원문 대신 **요약만** 돌아오는지 확인한다.
4. `model: haiku`를 지우고 다시 실행해, 부모 모델로 바뀌는지 확인한다.

### 실습 3: 선택 연습
다음 작업에 메인 / 서브에이전트 / 에이전트 팀 중 무엇이 맞는지 고르고 이유를 적어 보자.
1. 저장소 전체에서 특정 함수 호출 위치 찾기
2. 버그 원인에 대해 세 가지 가설을 서로 반박하며 검증하기
3. 화면 문구를 사용자와 하나씩 상의하며 고치기

<details>
<summary>예시 답</summary>

1. 서브에이전트 — 검색 결과가 장황하고 위치 목록만 필요하다
2. 에이전트 팀 — 가설끼리 서로 반박·공유가 필요하다
3. 메인 대화 — 사용자와 잦은 주고받기가 필요하다
</details>

## 7. 학습 체크리스트

- [ ] 서브에이전트가 보지 못하는 세 가지(대화 기록, 호출한 스킬, 읽은 파일)를 말할 수 있다
- [ ] 서브에이전트에게 일을 맡길 때 왜 맥락을 직접 적어 줘야 하는지 설명할 수 있다
- [ ] `tools`와 `disallowedTools`의 차이를 안다
- [ ] 메인 권한 모드가 서브에이전트 권한에 미치는 영향을 안다
- [ ] 스킬과 서브에이전트가 어떤 컨텍스트에서 실행되는지 구분할 수 있다
- [ ] 서브에이전트와 에이전트 팀의 소통·조율·비용 차이를 표 없이 설명할 수 있다
- [ ] 에이전트 팀의 네 가지 구성요소와 주요 제약을 말할 수 있다

## 핵심 정리

| 개념 | 한 줄 요약 |
|------|-----------|
| 메인 에이전트 | 세션 전체 기록을 보는 사용자와의 대화 그 자체 |
| 서브에이전트 | 격리된 컨텍스트에서 일하고 요약만 돌려주는 전문 조수 |
| 컨텍스트 격리 | 서브는 대화 기록·스킬·읽은 파일을 모른다 |
| 상속과 축소 | 도구는 상속 후 축소, 모델은 지정 가능, 권한은 메인 모드에 묶일 수 있음 |
| 에이전트 팀 | 서로 직접 대화하며 스스로 조율하는 여러 Claude 인스턴스 (실험 기능) |
| 선택 기준 | 주고받기 → 메인 / 결과만 → 서브 / 토론·협업 → 팀 |
